## Trovaglie

### [ALTA] #1 — QRandomGenerator::global() nel fallback HMAC-XOR (non crittograficamente sicuro)

**File**: `ble_crypto.h` righe 53, 205
**Descrizione**: Il generatore pseudocasuale `global()` di Qt non e' garantito crittograficamente sicuro — il suo seed e' basato su `qsrand`/`time()` e predicibile. Usato sia in `generateKey()` (fallback senza OpenSSL) sia nel salt del fallback `encrypt()`.

**Codice vulnerabile** (originale):
```cpp
const quint32 r = QRandomGenerator::global()->generate();
```

**Fix applicato**:
```cpp
auto rng = QRandomGenerator::securelySeeded();
const quint32 r = rng.generate();
```
`securelySeeded()` usa `/dev/urandom` o l'equivalente platform-specifico (Android: `getrandom(2)`). Applicato in entrambi i punti (generateKey() e fallback encrypt()).

### [ALTA] #2 — QSettings senza org/app name (chiave in path globale)

**File**: `ble_crypto.h` righe 66, 81
**Descrizione**: `QSettings s;` (costruttore vuoto) usa i valori di `QCoreApplication::organizationName()` e `applicationName()`, che nell'app Android sono impostati come `"Prismalux"`/`"Mobile"` solo in `main.cpp`. Se `loadOrCreateKey()` viene chiamata prima dell'init dell'applicazione (o in un contesto diverso), la chiave viene salvata in un path di settings diverso da quello del resto dell'app — potenzialmente un file `.ini` globale con permessi piu' aperti. Incoerenza rispetto a tutte le altre `QSettings("Prismalux", "Mobile")` nell'app.

**Fix applicato**:
```cpp
// PRIMA
QSettings s;
// DOPO
QSettings s("Prismalux", "Mobile");
```
Applicato in `loadOrCreateKey()` e `saveKey()`.

**Nota residua**: Su Android, `QSettings("Prismalux","Mobile")` scrive in `SharedPreferences` — file accessibile solo all'app stessa. Su Linux/desktop (dev), scrive in `~/.config/Prismalux/Mobile.conf`. In entrambi i casi e' il percorso corretto e gia' usato da tutta l'app. La chiave resta in chiaro (Base64) nell'archivio di settings — si raccomanda QKeychain per la versione finale (vedi #BASSA #1 sotto).

### [ALTA] #3 — Server RFCOMM con QBluetooth::NoSecurity (nessun pairing richiesto)

**File**: `ble_page.cpp` riga 565
**Descrizione**: Il server BT Classic imposta esplicitamente `NoSecurity`, il che significa che qualunque dispositivo nel raggio BT puo' connettersi al socket RFCOMM senza aver effettuato il pairing. L'unica difesa era l'encryption applicativa di BleCrypto — che pero' e' opt-in (default off, ora fixato). Un attaccante fisicamente vicino poteva connettersi, inviare frame in chiaro e ricevere broadcast di messaggi precedenti al momento dell'abilitazione della cifratura.

**Fix applicato**:
```cpp
// PRIMA
m_btServer->setSecurityFlags(QBluetooth::NoSecurity);
// DOPO
m_btServer->setSecurityFlags(QBluetooth::Authorization);
```
`Authorization` richiede che il dispositivo remoto sia gia' accoppiato (via PIN/SSP) prima che la connessione RFCOMM venga accettata. Questo aggiunge un secondo strato rispetto a BleCrypto.

### [MEDIA] #4 — Fallback decrypt() accede a frame[0] senza controllo isEmpty()

**File**: `ble_crypto.h` riga 245 (fallback HMAC-XOR)
**Descrizione**: La versione fallback di `decrypt()` controllava `key.size()` ma accedeva subito a `frame[0]` senza verificare che `frame` non fosse vuoto. Un frame BLE vuoto o malformato causava undefined behavior (lettura fuori bounds su QByteArray).

**Fix applicato**:
```cpp
if (frame.isEmpty()) return {};  // aggiunto prima di frame[0]
```
La versione GCM (con OpenSSL) era gia' corretta: `if (frame.size() < 1 + kIvLen + kTagLen) return {};`.

### [MEDIA] #5 — m_cryptoEnabled = false di default (cifratura opt-in)

**File**: `ble_page.h` riga 148
**Descrizione**: La cifratura AES-256-GCM era disabilitata di default. Ogni nuova chat aperta senza toccare il toggle inviava messaggi in chiaro sul canale BT. Con il fix #3 ora c'e' il pairing obbligatorio, ma i messaggi resterebbero comunque leggibili in chiaro da qualsiasi peer accoppiato.

**Fix applicato**:
```cpp
// PRIMA
bool m_cryptoEnabled = false;
// DOPO
bool m_cryptoEnabled = true;   // cifratura on per default — opt-out
```

### [BASSA] #6 — Chiave completa mostrata in QMessageBox (shoulder surfing)

**File**: `ble_page.cpp` riga 1072
**Descrizione**: `onShowKeyInfo()` mostra l'intera chiave a 32 byte (Base64, 44 caratteri) nel corpo del QMessageBox. Chiunque osservi lo schermo puo' fotografarla. La funzionalita' e' intenzionale (condivisione key con il peer), ma manca avviso esplicito sul rischio.

**Raccomandazione**: Aggiungere nel testo del dialog la frase
> "Attenzione: non mostrare questa chiave in pubblico. Condividila solo via canale sicuro (messaggio cifrato o QR privato)."

Non patchato — e' scelta UX, non falla critica.

---

### [BASSA] #7 — Nessun AAD (Additional Authenticated Data) in GCM

**File**: `ble_crypto.h` funzione `encrypt()`/`decrypt()` (path OpenSSL)
**Descrizione**: AES-256-GCM supporta AAD per autenticare metadati (es. UUID mittente, timestamp) senza cifrarli. Non usarlo non e' una falla — il tag GCM autentica il ciphertext — ma significa che un attaccante potrebbe intercettare e riscrivere il contesto di consegna (indirizzo BT, timestamp) senza invalidare il tag.

**Raccomandazione**: Per una futura versione, includere almeno l'indirizzo MAC sorgente nell'AAD via `EVP_EncryptUpdate(ctx, nullptr, &len, aad, aadLen)`.

---

### [BASSA] #8 — Commento onShareKey() in ble_page.h non implementato

**File**: `ble_page.h` riga 32
**Descrizione**: Il commento del costruttore cita `onShareKey()` come slot per condivisione via QR/PIN, ma lo slot non esiste nel header. Il pulsante "Chiave" chiama `onShowKeyInfo()` che mostra la chiave e offre copia negli appunti, senza QR.

**Raccomandazione**: Implementare `onShareKey()` con QR code generato a runtime (usa le librerie QR gia' presenti nell'app) oppure rimuovere il riferimento dalla documentazione.

---

### [INFO] #9 — Sync LAN: nessuna esposizione diretta della chiave BLE

**Verificato**: `/api/sync` in `lan_server.cpp` trasporta solo `quiz_stats` e knowledge base. La chiave BLE (`BleCrypto/session_key` in QSettings) non viene mai inviata al server LAN. Nessun rischio cross-canale BLE→LAN.

**Nota**: `/api/sync` usa HTTP plain, il token LAN e' trasmesso in chiaro se la porta e' 11500 (non TLS). Questo e' gia' noto e documentato.

### Valutazione post-patch

Con i 5 fix applicati:
- La generazione del materiale crittografico e' ora sicura su tutti i percorsi di build (con e senza OpenSSL).
- La chiave e' archiviata nello stesso store dell'app (nessuna dispersione).
- Il server BT richede pairing prima di accettare connessioni.
- La cifratura e' on-by-default — l'utente deve attivamente disabilitarla.
- Il crash su frame vuoto e' eliminato.

La crittografia GCM con OpenSSL rimane corretta: IV fresh 12 byte via RAND_bytes, tag 16 byte verificato in EVP_DecryptFinal_ex prima di restituire qualsiasi plaintext.
