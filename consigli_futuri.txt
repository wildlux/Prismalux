────────────────────────────────────────────────────────────────────────────────
  SEZIONE 2 — REGOLE Qt6 C++
────────────────────────────────────────────────────────────────────────────────

CONNECT():
  - Sempre sintassi puntatore-a-funzione: connect(src, &Cls::sig, ctx, &Cls::slot)
  - Context object (4° argomento) SEMPRE presente — evita dangling pointer
  - Lambda solo se < 2 righe E cattura solo oggetti figli del context
  - Logica > 2 righe → slot nominato nel .cpp

MEMORIA:
  - QPointer<T> per puntatori a widget che potrebbero essere distrutti
  - Mai delete manuale su QObject con parent → il parent lo gestisce
  - new QObject(this) → ownership automatica al parent

DPI / DIMENSIONI:
  - Tutte le dimensioni strutturali passano per dpiScale(N)
  - Mai px hardcoded: width(120) → dpiScale(120)
  - Font size: scalare con dpiScale o usare unità em in QSS

COSTANTI E PERCORSI:
  - File centralizzato config/app_config.h con namespace AppConfig
  - Porte, URL base, chiavi QSettings come constexpr o static const
  - Mai "localhost:11434" inline nel codice → AppConfig::kOllamaUrl

TEMA / STILE:
  - ThemeManager singleton con static ThemeManager inst(nullptr) — MAI inst(qApp)
  - QSS caricato da file .qss esterno, mai inline nel codice C++
  - objectName() per stili specifici, non puntatori di classe

INTERNAZIONALIZZAZIONE:
  - Ogni stringa visibile all'utente in tr("...")
  - Emoji e caratteri speciali: byte UTF-8 diretti (\xf0\x9f...) nei const char*
    invece di entity HTML per QTextBrowser (non supporta > U+FFFF)

TESTING:
  - Un file test_*.cpp per ogni modulo core (senza dipendenze UI)
  - ctest con RESOURCE_LOCK per test pesanti CPU
  - Test che richiedono servizi esterni: SKIP se servizio non disponibile
  - Target minimo: 80% copertura su logica core (no test UI automatizzati)

SICUREZZA:
  - Nessun input utente passa direttamente a QProcess/SQL/shell
  - Token API: QKeychain o env var — mai hardcoded, mai in git
  - Endpoint remoti: validare URL prima di fetch (schema https/http only)
  - Log: mai dati sensibili (token, password, PII)

  SEZIONE 4 — AGENTE SINGOLO: TEMPLATE STABILE
────────────────────────────────────────────────────────────────────────────────

Un agente stabile ha questi 5 componenti chiari:

1. SYSTEM PROMPT (fisso, caricato da file .txt esterno)
   - Identità e ruolo preciso (chi è l'agente)
   - Formato output atteso (JSON / markdown / testo libero)
   - Limiti espliciti (cosa NON deve fare)
   - Lingua di risposta
   - Esempio di input/output se il task è ambiguo

2. CONTESTO DINAMICO (iniettato a runtime)
   - RAG: chunk rilevanti recuperati prima della chiamata
   - Memoria: ultimi N turni della sessione
   - Stato applicazione: dati specifici del task attuale
   - Limite: non superare 60% della context window con contesto

3. INPUT UTENTE
   - Validato prima di arrivare all'agente
   - Lunghezza massima definita (es. 4096 token)
   - Sanitizzato da prompt injection (cerca pattern "ignora le istruzioni")

4. GESTIONE OUTPUT
   - Se JSON atteso: validare schema prima di usarlo
   - Se risposta vuota: retry con messaggio di errore esplicito (max 3 volte)
   - Strip di tag interni (<think>, <reasoning>) prima di mostrare all'utente
   - Fallback se il modello non risponde nel formato atteso

5. ERRORI E TIMEOUT
   - Timeout esplicito su ogni chiamata (es. 120 secondi)
   - Distinguere: errore rete / errore modello / risposta malformata / abort utente
   - Log di ogni chiamata con timestamp, modello, token usati
   - Mai mostrare stack trace all'utente finale

TEMPLATE SYSTEM PROMPT AGENTE:
   Sei [RUOLO]. Il tuo compito è [OBIETTIVO SPECIFICO].
   Rispondi SEMPRE in [LINGUA].
   Formato risposta: [JSON con schema X / markdown / testo libero].
   Non fare: [lista di comportamenti da evitare].
   Se non sai rispondere: di' esplicitamente "Non lo so" invece di inventare.
   Esempio input: [...]
   Esempio output: [...]

  SEZIONE 5 — SWARM DI AGENTI: TEMPLATE STABILE
────────────────────────────────────────────────────────────────────────────────

Uno swarm stabile segue questo schema:

COORDINATORE (Master Agent)
  - Riceve il task originale dall'utente
  - Produce un piano JSON con subtask e dipendenze
  - Schema piano: { "task": "...", "subtasks": [
      { "id": 1, "role": "...", "prompt": "...", "depends_on": [] },
      { "id": 2, "role": "...", "prompt": "...", "depends_on": [1] }
    ]}
  - Non esegue mai lavoro diretto — solo pianifica e sintetizza

SUB-AGENTI (Workers)
  - Un ruolo specifico ciascuno (Ricercatore, Critico, Scrittore, ecc.)
  - Ricevono: prompt del task + output dei predecessori (depends_on)
  - Restituiscono: testo o JSON strutturato — mai chiamate ad altri agenti
  - Timeout individuale per agente

ESECUZIONE
  - Ordine topologico (BFS su depends_on) — rispetta le dipendenze
  - Agenti senza dipendenze possono girare in parallelo (QFuture/thread pool)
  - Ogni risultato viene salvato in memoria persistente (GraphMemory o DB)
  - Se un sub-agente fallisce: registra l'errore, continua con gli altri

SINTESI FINALE
  - Il Coordinatore riceve tutti i risultati
  - Produce una risposta coerente citando i contributi di ogni agente
  - Salva il risultato finale in memoria con importanza alta

ANTI-PATTERN DA EVITARE:
  - Agenti che chiamano altri agenti in cascata infinita
  - Nessun limite al numero di subtask (metti un tetto: es. max 10)
  - Context window che cresce senza limite (tronca i risultati lunghi)
  - Nessun meccanismo di abort utente durante l'esecuzione
  - Risultati non salvati (se crasha si riparte da zero)

  SEZIONE 6 — MEMORIA PERSISTENTE
────────────────────────────────────────────────────────────────────────────────

Tre livelli di memoria da implementare sempre:

LIVELLO 1 — SESSIONE (in RAM, dura finché l'app è aperta)
  - Cronologia turni (max N turni configurabile)
  - Stato agente corrente
  - Buffer token streaming

LIVELLO 2 — APPLICAZIONE (file locale, dura tra riavvii)
  - QSettings per preferenze UI e configurazioni
  - SQLite per dati strutturati (GraphMemory, cronologia chat)
  - File .txt/.json per snapshot esportabili

LIVELLO 3 — CONOSCENZA (RAG, cresce nel tempo)
  - Documenti indicizzati con embedding
  - Grafo di entità e relazioni (nodi + archi)
  - Aggiornamento incrementale (non ricalcolare tutto ogni volta)

REGOLA CRITICA: ogni scrittura su LIVELLO 2 e 3 deve essere atomica.
Se l'app crasha a metà scrittura, il file non deve essere corrotto.
Usa transazioni SQLite o scrittura su file temporaneo + rename atomico.

  └── web/
      ├── index.html              ← shell HTML (una sola pagina)
      ├── app.js                  ← logica JS: fetch, WebSocket, router
      ├── style.css               ← stile (CSS variabili per temi)

ENDPOINTS REST (da definire in api_handlers.cpp):
  GET    /api/notes               ← lista note (JSON array)
  POST   /api/notes               ← crea nota { title, body }
  PUT    /api/notes/:id           ← modifica nota
  DELETE /api/notes/:id           ← elimina nota
  POST   /api/chat                ← domanda AI, risposta in streaming (SSE)
  GET    /api/models              ← lista modelli Ollama disponibili
  GET    /health                  ← heartbeat (200 OK)

FRONTEND app.js (pattern minimo stabile):
  // Router hash-based — niente framework, zero dipendenze
  const routes = { '#/notes': showNotes, '#/chat': showChat, '#/settings': showSettings };
  window.addEventListener('hashchange', () => (routes[location.hash] || showNotes)());

  // Streaming AI via Server-Sent Events
  async function askAI(question, onToken, onDone) {
    const res = await fetch('/api/chat', {
      method: 'POST',
      headers: { 'Content-Type': 'application/json' },
      body: JSON.stringify({ question })
    });
    const reader = res.body.getReader();
    const dec = new TextDecoder();
    while (true) {
      const { done, value } = await reader.read();
      if (done) { onDone(); break; }
      onToken(dec.decode(value));
    }
  }

  // Nessun innerHTML con dati utente — sempre textContent o DOMPurify
  function renderNote(note) {
    const div = document.createElement('div');
    div.className = 'note-card';
    const title = document.createElement('h3');
    title.textContent = note.title;   // sicuro: no XSS
    div.appendChild(title);
    return div;
  }

9.6 — SWARM DI AGENTI PER NoteAI (esempio pratico)
────────────────────────────────────────────────────────────────────────────────

Caso d'uso: l'utente scrive "analizza le mie note e dimmi cosa devo fare questa settimana"

PIANO JSON DEL COORDINATORE:
  {
    "task": "Analisi note settimanale con raccomandazioni",
    "subtasks": [
      {
        "id": 1, "role": "Lettore",
        "prompt": "Leggi tutte le note degli ultimi 7 giorni e categorizzale per tema.",
        "depends_on": []
      },
      {
        "id": 2, "role": "Analista Priorità",
        "prompt": "Dalla categorizzazione, identifica le 3 attività più urgenti.",
        "depends_on": [1]
      },
      {
        "id": 3, "role": "Analista Rischi",
        "prompt": "Dalla categorizzazione, identifica cosa è rimasto in sospeso da più di 3 giorni.",
        "depends_on": [1]
      },
      {
        "id": 4, "role": "Pianificatore",
        "prompt": "Crea un piano settimanale concreto combinando priorità e rischi.",
        "depends_on": [2, 3]
      }
    ]
  }

ESECUZIONE:
  - Agente 1 gira subito (no depends_on)
  - Agenti 2 e 3 girano in PARALLELO dopo che 1 è completato
  - Agente 4 gira solo dopo che 2 e 3 sono entrambi completati
  - Coordinatore sintetizza il risultato di Agente 4 in linguaggio naturale

IMPLEMENTAZIONE IN Qt6 (pseudocodice):
  void runSwarm(const QJsonArray& subtasks) {
    // Ordina per dipendenze (topological sort)
    auto sorted = topoSort(subtasks);
    for (const auto& group : sorted) {  // group = agenti senza dipendenze pendenti
      QList<QFuture<QString>> futures;
      for (const auto& task : group) {
        futures << QtConcurrent::run([task, this]() {
          return m_ai->chatSync(buildAgentPrompt(task), buildAgentContext(task));
        });
      }
      // Attendi tutti del gruppo prima di passare al prossimo
      for (auto& f : futures) { f.waitForFinished(); saveResult(f.result()); }
    }
    synthesize();  // Coordinatore legge tutti i risultati e produce la risposta finale
  }

  SEZIONE 10 — COME FARE UN SaaS (Software as a Service)
────────────────────────────────────────────────────────────────────────────────

Un SaaS è la stessa app dell'esempio NoteAI, ma spostata sul cloud e venduta
come abbonamento mensile. L'utente non installa niente: apre il browser e paga.

La differenza rispetto a un'app locale:
  App locale  → un utente, un dispositivo, dati suoi, nessun pagamento ricorrente
  SaaS        → molti utenti, qualsiasi dispositivo, dati isolati per utente,
                abbonamento mensile/annuale, tu gestisci i server

10.2 — MULTI-TENANCY: isolare i dati di ogni utente
────────────────────────────────────────────────────────────────────────────────

Multi-tenancy = molti utenti (tenant) sulla stessa istanza del software,
ognuno vede SOLO i propri dati. È il cuore tecnico di ogni SaaS.

3 STRATEGIE (ordine: semplicità → isolamento):

STRATEGIA A — Row-Level (una sola tabella, colonna user_id):
  CREATE TABLE notes (
    id         UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    user_id    UUID NOT NULL REFERENCES users(id) ON DELETE CASCADE,
    title      TEXT NOT NULL,
    body       TEXT,
    created_at TIMESTAMPTZ DEFAULT now()
  );
  CREATE INDEX idx_notes_user ON notes(user_id);

  Ogni query DEVE filtrare per user_id — mai dimenticare il WHERE.
  Vantaggio: semplicissimo. Svantaggio: un bug = dati di tutti esposti.
  Quando usarla: fino a ~10.000 utenti, basso rischio compliance.

STRATEGIA B — Schema separato per tenant (PostgreSQL schemas):
  -- Per ogni nuovo utente che si registra:
  CREATE SCHEMA tenant_<user_uuid>;
  CREATE TABLE tenant_<user_uuid>.notes (id UUID, title TEXT, body TEXT, ...);

  Vantaggio: isolamento forte, facile backup per singolo utente.
  Svantaggio: migration complessa (devi eseguirla su ogni schema).
  Quando usarla: ~10.000–100.000 utenti, requisiti GDPR forti.

STRATEGIA C — Database separato per tenant:
  Ogni azienda cliente ha il suo database PostgreSQL.
  Vantaggio: isolamento totale, possibile on-premise per clienti enterprise.
  Svantaggio: costoso, difficile da gestire.
  Quando usarla: enterprise B2B con contratti >10.000€/anno.

CONSIGLIO PRATICO: inizia con Strategia A. Aggiungi Row-Level Security
di PostgreSQL come seconda difesa:
  ALTER TABLE notes ENABLE ROW LEVEL SECURITY;
  CREATE POLICY notes_user_isolation ON notes
    USING (user_id = current_setting('app.current_user_id')::UUID);

────────────────────────────────────────────────────────────────────────────────
10.3 — AUTENTICAZIONE: chi sei e cosa puoi fare
────────────────────────────────────────────────────────────────────────────────

FLUSSO REGISTRAZIONE / LOGIN:
  1. Utente inserisce email + password
  2. Backend: hash password con bcrypt (cost factor 12) — MAI MD5/SHA1
  3. Backend: genera JWT (JSON Web Token) firmato con chiave privata RS256
  4. Frontend: salva JWT in httpOnly cookie — MAI in localStorage (XSS)
  5. Ogni richiesta API: JWT nell'header Authorization: Bearer <token>
  6. Backend: verifica firma JWT, estrae user_id, filtra dati per quel user_id

SCHEMA DATABASE AUTENTICAZIONE MINIMO:
  CREATE TABLE users (
    id              UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    email           TEXT UNIQUE NOT NULL,
    password_hash   TEXT NOT NULL,          -- bcrypt, mai testo chiaro
    email_verified  BOOLEAN DEFAULT false,
    plan            TEXT DEFAULT 'free',    -- 'free' | 'pro' | 'enterprise'
    stripe_customer_id TEXT,               -- ID cliente Stripe
    created_at      TIMESTAMPTZ DEFAULT now(),
    last_login_at   TIMESTAMPTZ
  );

  CREATE TABLE refresh_tokens (
    id          UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    user_id     UUID REFERENCES users(id) ON DELETE CASCADE,
    token_hash  TEXT NOT NULL,              -- hash del refresh token
    expires_at  TIMESTAMPTZ NOT NULL,
    revoked     BOOLEAN DEFAULT false
  );

JWT: due token (pattern sicuro):
  Access token  → validità 15 minuti, in memoria JS o cookie httpOnly
  Refresh token → validità 30 giorni, SOLO in cookie httpOnly Secure SameSite=Strict
  Al refresh: invalida il vecchio, emetti nuovo. Rotazione ad ogni uso.

OPZIONE ALTERNATIVA — Usa un servizio esterno (consigliato per iniziare):
  Clerk.dev, Auth0, Supabase Auth — gestiscono tutto (MFA, OAuth, email).
  Costo: gratis fino a ~10.000 utenti attivi/mese.
  Vantaggio: non devi gestire la sicurezza dell'autenticazione tu.

10.4 — PAGAMENTI: Stripe (il modo più rapido per iniziare)
────────────────────────────────────────────────────────────────────────────────

CONCETTI STRIPE DA SAPERE:
  Customer   → un utente nel tuo SaaS (creato alla registrazione)
  Product    → il tuo piano (es. "NoteAI Pro")
  Price      → il prezzo del piano (es. €9,99/mese o €99/anno)
  Subscription → un Customer abbonato a un Price
  Webhook    → Stripe chiama il tuo backend quando succede qualcosa

FLUSSO ABBONAMENTO (dall'utente al tuo conto in banca):
  1. Utente clicca "Passa a Pro"
  2. Frontend chiama il tuo backend: POST /api/billing/create-checkout
  3. Backend chiama Stripe API: crea una Checkout Session con il Price ID
  4. Backend risponde con l'URL della pagina Stripe
  5. Frontend reindirizza l'utente su stripe.com/pay/cs_live_...
  6. Utente inserisce carta su Stripe (tu non vedi MAI i dati carta)
  7. Stripe processa il pagamento
  8. Stripe invia webhook al tuo backend: POST /api/webhooks/stripe
  9. Backend riceve evento "checkout.session.completed"
  10. Backend aggiorna users.plan = 'pro' nel database
  11. Stripe reindirizza utente su /success?session_id=...
  12. Frontend mostra "Benvenuto in Pro!"

IMPLEMENTAZIONE BACKEND (Python FastAPI — il più semplice):
  import stripe
  stripe.api_key = os.getenv("STRIPE_SECRET_KEY")  # mai hardcoded

  @app.post("/api/billing/create-checkout")
  async def create_checkout(user: User = Depends(get_current_user)):
      session = stripe.checkout.Session.create(
          customer=user.stripe_customer_id,
          payment_method_types=["card"],
          line_items=[{"price": "price_XXXXX", "quantity": 1}],
          mode="subscription",
          success_url="https://tuodominio.com/success?session_id={CHECKOUT_SESSION_ID}",
          cancel_url="https://tuodominio.com/pricing",
      )
      return {"checkout_url": session.url}

  @app.post("/api/webhooks/stripe")
  async def stripe_webhook(request: Request):
      payload = await request.body()
      sig = request.headers.get("stripe-signature")
      event = stripe.Webhook.construct_event(
          payload, sig, os.getenv("STRIPE_WEBHOOK_SECRET")
      )
      if event["type"] == "checkout.session.completed":
          session = event["data"]["object"]
          await db.update_user_plan(session["customer"], "pro")
      elif event["type"] == "customer.subscription.deleted":
          await db.update_user_plan(session["customer"], "free")
      return {"status": "ok"}

10.6 — SICUREZZA SaaS: le 10 regole che non si saltano mai
────────────────────────────────────────────────────────────────────────────────

  1. HTTPS OVUNQUE — Let's Encrypt gratis, rinnovato automaticamente da Certbot.
     Nessuna eccezione. Nessun redirect HTTP→HTTPS "per dopo".

  2. VARIABILI D'AMBIENTE — Mai chiavi/password nel codice o in git.
     Usa .env locale + GitHub Secrets per CI/CD + Vault per produzione.

  3. RATE LIMITING — Limite su ogni endpoint pubblico.
     Login: max 5 tentativi/minuto per IP. API: max 100 req/minuto per utente.
     Nginx o Redis + sliding window.

  4. INPUT VALIDATION — Valida tutto quello che arriva dall'esterno.
     Schema Pydantic (Python) o Zod (TypeScript) su ogni endpoint.
     MAI fidarsi del frontend per la validazione.

  5. SQL INJECTION — Sempre query parametrizzate. Mai f-string in SQL.
     SBAGLIATO: f"SELECT * FROM notes WHERE id = {user_input}"
     CORRETTO:  "SELECT * FROM notes WHERE id = $1", [user_input]

  6. XSS — Mai inserire HTML con dati utente senza sanitizzazione.
     Frontend: textContent invece di innerHTML per dati utente.
     Backend: escape HTML output. Usa DOMPurify se devi rendere HTML.

  7. CORS — Whitelist esplicita dei domini autorizzati.
     MAI allow_origins=["*"] in produzione.

  8. GDPR (se hai utenti europei) — Obbligatorio:
     - Privacy policy chiara e leggibile
     - Cookie banner con consenso esplicito
     - Endpoint DELETE /api/me per cancellare account e tutti i dati
     - Data export: GET /api/me/export per scaricare tutti i propri dati
     - Dati salvati SOLO in EU (Hetzner Frankfurt, AWS eu-central-1, ecc.)

  9. BACKUP — Backup automatico database ogni 24 ore.
     Test ripristino ogni mese (un backup non testato non vale niente).
     Retention: 7 giorni rolling + 1 snapshot mensile per 12 mesi.

  10. MONITORING — Sentry per error tracking (gratis fino a 5.000 errori/mese).
      Uptime Robot per availability (alert se giù da >1 minuto) — gratis.
      Log strutturati (JSON) con timestamp, user_id, endpoint, status code.
